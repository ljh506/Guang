## 1. AI 识别原理

### 1.1 链路结构

输入图片 → AI 识别服务（backend 注入）→ 类别标准化 → 置信度阈值分流 → 失败兜底

| 环节 | 交付模块 | 职责 |
|---|---|---|
| 识别调用封装 | Day2 `ai_client.py` | 封装视觉服务调用，返回 `label` + `confidence`，支持 backend 注入与 Mock 模拟 |
| 类别标准化 | Day4 `category_normalizer.py` | 统一 10 类体系，同义词表 + 关键词包含 + 兜底映射 |
| 识别链路 | Day5 `recognition_pipeline.py` | 整合上述环节，输出统一结构，支持 image_path / image_bytes 双入口 |
| 失败提示 | Day12 `user_prompt.py` | 识别失败 / 低置信度时生成用户提示文案 |

### 1.2 阈值分流（与 Day2 一致）

| 置信度区间 | status | 行为 |
|---|---|---|
| confidence >= 0.80 | `auto_fill` | 自动填充类别，无需人工介入 |
| 0.60 <= confidence < 0.80 | `manual_confirm` | 前端弹出确认框，人工确认 |
| confidence < 0.60 或缺失 | `manual_select` | 人工从 10 个类别下拉选择 |
| 服务异常 / 超时 | `fallback` | 走兜底：提供 `available_categories` 全类别列表，附 `fallback_reason` |

### 1.3 统一返回结构（`RecognitionPipeline.recommend()`）

```python
{
    "category_id": str | None,      # 标准化后的类别ID（Day4 统一 10 类）
    "category_name": str | None,    # 类别中文名
    "confidence": float,            # 标准化调整后的置信度 0~1
    "need_confirm": bool,           # 是否需要人工介入
    "matched_by": str | None,       # alias / keyword / fallback 命中方式
    "fallback": bool,               # 是否走失败兜底
    "available_categories": [{"category_id", "category_name"}, ...],  # 供下拉渲染
    "status": str,                  # auto_fill / manual_confirm / manual_select / fallback
    "fallback_reason": str | None,  # 兜底原因（如"AI识别服务不可用"、"识别超时"）
    "raw_label": str | None,        # 识别服务原始标签
}
```

### 1.4 backend 约定

- 签名：`backend(image_path) -> {"label": str, "confidence": float}`
- 失败：抛 `TimeoutError` / `ConnectionError` / `ValueError` 等异常，由 pipeline 捕获转为 `fallback`
- 未配置 backend 时默认抛 `RuntimeError("未配置 AI 识别服务 backend，默认走失败兜底")`

## 2. 估价规则原理（Day6/Day7）

### 2.1 核心公式

估价区间 = 原价 × 品相折扣（category_id + condition 查折扣表），再叠加使用年限微调：

```
estimated_min = round(original_price * discount_low)
estimated_max = round(original_price * discount_high)
```

- 输出满足：`min <= max`、整数元、非赠送且原价 > 0 时保底 1 元、`reason_text` 可解释。
- **asking_price（用户手填标价）与估价区间分离**：AI 只出区间，用户以 asking_price 为准参与匹配价格维度。

### 2.2 折扣表（核心四类，与计划书一致）

| category_id | new_like | good | fair |
|---|---|---|---|
| textbook | 0.60 ~ 0.80 | 0.40 ~ 0.60 | 0.20 ~ 0.40 |
| electronics | 0.70 ~ 0.85 | 0.50 ~ 0.70 | 0.10 ~ 0.50 |
| life_goods | 0.50 ~ 0.70 | 0.40 ~ 0.50 | 0.10 ~ 0.40 |
| clothing | 0.40 ~ 0.60 | 0.30 ~ 0.40 | 0.15 ~ 0.30 |

其余六类（stationery / digital_accessories / sports_equipment / furniture / other_books / other）沿用 Day2 自拟合理值，见 `price_engine_day7.py` 常量 `DISCOUNT_TABLE`。

### 2.3 边界与异常规则（Day7 加固）

| 场景 | 处理 |
|---|---|
| 原价缺失 | 错误码 `PRICE_ORIGINAL_REQUIRED` |
| 原价 NaN / 非数字 / bool | `PRICE_INVALID_FORMAT`（拦截 NaN 避免 round() 崩溃；拦截 bool 避免 float(True)=1.0 误导） |
| 原价 > 100000 或 inf | `PRICE_OUT_OF_RANGE` |
| 品相缺失 / 非法 | `CONDITION_REQUIRED` / `CONDITION_INVALID` |
| 类别不在折扣表 | `CATEGORY_INVALID` |
| 免费赠送（原价 0） | 直接 0 元区间，reason 注明"免费赠送" |
| 使用年限为负数 / 非数字 / 非有限值 | 忽略微调、走原始折扣（不崩溃） |
| 电子产品使用年限 | 0~6 月：0.70~0.80；6~12 月：0.65~0.75；12~24 月：0.55~0.70；>24 月：降档至良好档 |

### 2.4 输出字段

`estimated_min` / `estimated_max` / `reason_text` / `rule_ref` / `price_tip`（或 `error` 错误码）。

## 3. 匹配算法原理（Day9）

### 3.1 公式

```
MatchScore = 0.50 × Score_category_wish + 0.30 × Score_price + 0.20 × Score_school
```

权重合计 1.0；匹配度保留 4 位小数。

### 3.2 类别/意愿分（50%）

| 情形 | 得分 |
|---|---|
| 双向完全匹配（A 物品 ∈ B 意愿 且 B 物品 ∈ A 意愿） | 1.0 |
| 双向类别匹配（无显式意愿，双方在售类别一致） | 0.9 |
| 单向匹配（仅一方物品在对方意愿中） | 0.5 |
| 类别完全不匹配 | 0.0（不进候选） |

### 3.3 价格接近分（30%）

```
ratio = |a - b| / max(a, b)；Score = 1.0 - ratio
```

| 情形 | 得分 |
|---|---|
| 双方标价相同 | 1.0 |
| 双方均免费（0 元） | 1.0 |
| 仅一方免费 | 0.3 |
| 标价缺失 / 非法（bool / NaN / 负数） | 0.0 |

### 3.4 同校优先分（20%）

- school_id 相同 → 1.0；不同或缺失 → 0.0

### 3.5 分级阈值与排序

| 匹配度 | level | 行为 |
|---|---|---|
| >= 0.75 | `high` | 高匹配，进入推荐；可触发状态机自动流转 |
| >= 0.50 | `normal` | 普通匹配，进入推荐 |
| < 0.50 | `low` | 不进推荐列表 |

- 排序：总分降序 → 价格接近度降序 → 发布时间近者优先；单次最多 20 条。
- 去重：同一对 `(user, goods)` 已有未完成 Exchange 记录时不重复生成推荐。

### 3.6 输入字段

至少含 `category_id`、`wish_category_id`（str/list，可缺省）、`asking_price`、`school_id`，可选 `status` / `estimated_min` / `estimated_max` / `publish_time` / `goods_id` / `user_id`。状态非 `on_sale/active/available/可交换` 的不可交换物品不进候选。

## 4. 匹配解释与交换协议（Day10）

### 4.1 解释文本

`match_explanation.build_match_explanation()` 依据 Day1 细则模板生成可读解释：

```
双方意愿匹配（{A类别}↔{B类别}），双方标价 {a} 元与 {b} 元接近度 {p}%，
{同校/跨校}，综合匹配度 {s}%。
```

免费 / 价格缺失场景有独立文案分支，不可匹配时返回 None 不崩溃。

### 4.2 交换协议卡片

`build_exchange_protocol_text()` 输出协议文本；`validate_protocol()` 校验状态流转合法性（见下节状态机）。

## 5. 交易状态机衔接（Day8 → Day10）

### 5.1 状态流

```
chatting -> matched -> negotiating -> confirmed（-> 后续交付/完成）
```

`chat_rules.py`（Day8）提供 `validate_transition(from, to)` 校验合法流转；`TRADE_STATES` 定义状态集合。

### 5.2 on_match 衔接（Day9）

- 当前状态为 `chatting` 且匹配度 >= 0.75（高匹配）→ 返回合法流转建议 `matched`；
- 未达高匹配 → 返回不建议自动流转（人工仍可发起）。

## 6. 用户提示优化（Day12）

`user_prompt.py` 依据 Day5 识别状态与 Day7 估价错误码生成用户提示：

| 入口 | 触发场景 | 输出 |
|---|---|---|
| `build_recognition_tip(status, ...)` | 识别失败 / 低置信度 / 需人工选择 | 分级提示文案（自动填充 / 人工确认 / 人工选择 / 失败兜底） |
| `build_price_tip(error/price_tip, ...)` | 估价异常（原价缺失 / 格式错误 / 超范围 / 品相缺失） | 可操作的修复引导文案 |
| `build_publish_tips(...)` | 发布页组合 | 识别 + 估价 + 标价提示的完整组合入口 |

提示文案区分"自动修复引导"与"人工介入引导"两类，保证用户在任何异常分支都有下一步动作指引。
