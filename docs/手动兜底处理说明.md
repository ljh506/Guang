# 拾光Agent 成员B · 手动兜底处理说明（Day15）

> 任务来源：项目计划书 Day 15 行，成员B 当日任务「最终检查 AI 识别 / 估价 / 匹配 算法，准备手动兜底」。
> 本文档说明当算法链路不可用、边界数据异常或自动流程无法推进时，各环节的**人工介入流程与后端约定**，供成员C（前端）、成员D（发布/交换）、成员E（测试）在联调与验收时执行。

---

## 1. AI 识别兜底

### 1.1 触发条件

| status | 触发条件 | 前端动作 |
|---|---|---|
| `manual_confirm` | 0.60 <= confidence < 0.80 | 弹出确认框，展示 `raw_label` 与识别类别，用户确认/修正 |
| `manual_select` | confidence < 0.60 或缺失 | 从 `available_categories`（10 个一级类别）下拉手动选择 |
| `fallback` | 服务不可用 / 超时 / 返回无标签 / 图片输入无效 | 按 `fallback_reason` 展示错误提示，同时提供全类别下拉手动选择 |

### 1.2 人工操作流程

1. 前端收到 `status=manual_select` 或 `fallback` 时，渲染 `user_prompt.build_recognition_tip(result)` 的 `title/message/action`；
2. 用户从 `available_categories` 中选择类别 → 前端以该 `category_id` 继续后续估价流程；
3. 后端不强制识别成功：`category_id` 由用户手动选择即可写入商品。

### 1.3 约定

- `available_categories` 始终返回 Day4 统一 10 类（`build_available_categories()`）；
- 识别服务恢复后无需清理旧数据，`status` 字段仅影响 UI 交互分支。

## 2. 估价异常兜底

### 2.1 错误码与人工修正动作

| 错误码 | 含义 | 用户修正动作 |
|---|---|---|
| `PRICE_ORIGINAL_REQUIRED` | 未填参考原价 | 前端引导用户填写原价（免费赠送可勾选 `is_free=True`） |
| `PRICE_INVALID_FORMAT` | 原价格式错误（NaN/非数字/bool） | 提示"请输入数字"，重新输入 |
| `PRICE_OUT_OF_RANGE` | 原价超上限（>100000） | 提示修改原价，或联系管理员 |
| `CONDITION_REQUIRED` | 未选品相 | 引导用户选择全新/良好/一般 |
| `CONDITION_INVALID` | 品相取值非法 | 重新选择 |
| `CATEGORY_INVALID` | 类别不在折扣表 | 检查 category_id 是否在统一 10 类内 |

### 2.2 人工操作流程

1. `estimate_price()` 返回 `{"error": {error_code, message}}`；
2. 前端渲染 `user_prompt.build_price_tip(result)` 的 `title/message/action`；
3. 用户按 action 修正后重新提交；**所有字段均合法后**才允许发布。

### 2.3 约定

- `asking_price` 为**用户手填真实标价**，AI 估价区间仅作参考展示，不强制等于 asking_price；
- 估价成功且 asking_price 明显偏离区间时，`price_tip` 给出黄色参考提示，不阻断发布。

## 3. 匹配与交换人工介入

### 3.1 匹配度不足（low < 0.50）

- 自动推荐不展示低匹配候选；
- 用户仍可通过搜索/浏览自行发起交换：后端允许人工发起，`on_match()` 返回"不建议自动流转"，状态机保持 `chatting`，不自动推进。

### 3.2 状态机人工操作

| 操作 | 合法流转 | 说明 |
|---|---|---|
| 发起交换 | chatting -> matched（高匹配自动建议） | 未达 0.75 时人工确认后仍可发起 |
| 协商 | matched -> negotiating | 双方进入协议协商 |
| 确认 | negotiating -> confirmed（需 confirm_a 与 confirm_b 双确认） | 单方确认不生效 |
| 取消 | 任意态 -> 取消态（成员A 定义） | 由后端 Exchange 状态机统一处理 |

- 协议卡片渲染使用 `build_exchange_protocol_text(goods_a, user_a, goods_b, user_b)`；
- 协议生成前必须通过 `validate_protocol()`：状态合法 + 双确认齐全 + 双方物品可交换。

### 3.3 人工兜底动作

- 若算法推荐为空但用户坚持交换：直接人工创建 Exchange 记录（state=negotiating），跳过推荐；
- 若协议校验失败：前端展示 `reason`，引导用户补充确认标记或修正状态。
